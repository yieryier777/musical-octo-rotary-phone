Agent、大模型的上下文、Skill —— 三个概念的关系

Agent 是"做事的主体"，上下文是"它此刻所知的一切"，Skill 是"沉淀成文件、按需注入的方法"。三者拼在一起，才是一台能干活的 AI。
生成日期：2026-09-09 基于同目录三份概念学习资料

一个类比先建立直觉

把 Agent 想成一位新来的实习生：

  • 上下文 = 他此刻脑子里知道的一切——写在他面前那块白板上的内容，擦掉就忘；
  • Skill = 公司发给他的 SOP 手册，平时只露出一页目录，接到对应任务时才翻到那一章；
  • Agent = 实习生本人 + 电脑权限 + "干到做完为止"的授权。

白板上写着什么，决定他这一步怎么做；手册按需摊开在白板上，让他的做法符合公司规范。三者缺一不可：没有白板（上下文）他不知道现状，没有手册（Skill）他每次都凭感觉，没有循环授权（Agent）他只会给建议不会动手。

三条核心关系

关系一：上下文决定 Agent 的每一步

Agent 循环的每一轮，模型都只能基于当前上下文做决策：系统提示给了角色，对话历史给了任务，工具返回结果给了"世界现状"。上下文里没有的信息，模型就当不存在——所以 Agent 的决策质量上限，就是它上下文的质量（Garbage in, garbage out）。上下文的有限性和位置敏感性，也直接约束 Agent：任务太长需要压缩历史，关键指令要放在开头或结尾。

关系二：Skill 通过上下文起作用

Skill 并不改变模型本身，它的生效方式恰恰是"在对的时机，把对的方法放进上下文"。因此 Skill 是上下文工程的一种持久化形式：把"做这类任务的方法"从一次性的口头交代，固化为可版本管理、可分享、可迭代的文件。Skill 的"渐进披露"设计（平时只暴露元数据）正是对上下文有限性的尊重——不舍得浪费白板上的一寸空间。

关系三：Agent 让 Skill 真正有用武之地

如果模型只会一问一答，Skill 里写的"十步流程"最多换来一段更长的回答；正因为 Agent 能循环地读上下文、调工具、看结果，Skill 中的流程才能被真正执行——每一步的产出（工具结果、中间产物）写回上下文，支撑下一步。换句话说：Skill 描述"该怎么做"，Agent 负责"真的去做"。

真实例证：一次作业里的三个概念

本仓库的诞生过程就是三者协作的完整链路：

  1. 我说："帮我完成这份作业"（用户目标）；
  2. WorkBuddy 作为 Agent 开始循环：读作业要求 → 检查 git 环境 → 克隆仓库 → 发现 github.com 无法直连 → 改用 API；
  3. 每一轮它"知道"的东西——作业要求、命令输出、报错文本——全部在上下文里，报错留在上下文中，才有了"换 API 通道"这个决策；
  4. 我让它学习三个概念时，Skill（concept-learning）的正文被注入上下文，十步流程因此被稳定执行——三次学习，同一份方法，零重复交代。

如果其中任何一环缺失：没有 Agent，方法只能换来一段文字建议；没有上下文管理，长对话会让它"忘记"作业要求；没有 Skill，每次学习都要从零口述一遍要求。

我的总结（个人理解）

学完三个概念后，我的整体判断是：它们分别对应"算力之外的三个杠杆"——行动杠杆（Agent）、信息杠杆（上下文）、知识杠杆（Skill）。

模型本身的能力是给定的，但同一个模型，配上循环与工具就成了 Agent，喂对信息（上下文工程）就能做出更好的决策，沉淀好方法（Skill）就能把一次性的成功变成可复用的流程。三者中，上下文是枢纽：Agent 的每次决策读它，Skill 的生效靠它。所以"用好 AI"很大程度上是"管好它每次看到什么"。

这也是为什么我认为这次作业的设计很巧：我们用 Agent 完成作业，用上下文理解原理，最后用 Skill 把整个学习方法沉淀下来——工具、原理、沉淀，正好闭环。
