Skill（智能体技能）

一句话定位：把"完成某类任务的方法"写成一份带元数据的结构化文档（SKILL.md），存放在约定位置，在合适的时机被注入模型上下文，让 AI 按这套方法做事。
生成日期：2026-09-09 由 concept-learning Skill 生成 领域：AI 工程实践

学习目标

  1. 能说清 Skill 与一次性提示词（Prompt）的区别，以及 Skill 解决了什么问题；
  2. 能描述 SKILL.md 的文件结构（YAML 元数据 + Markdown 正文）与两个存放层级；
  3. 能解释 Skill 的加载机制——为什么采用"按需注入、渐进披露"；
  4. 能动手为自己的重复性任务设计一个可复用的 Skill。

核心问题

  • 每次把要求写进提示词不行吗？Skill 的价值到底在哪里？
  • Skill 是怎么被"触发"和"加载"的？
  • Skill、工具（Tool）、微调（Fine-tuning）分别适合沉淀什么？
  • 一个好 Skill 的判断标准是什么？

我的解释

我发现每次让 AI 帮我学新概念时，都要重复交代同一套要求："给我学习目标、用自己的话解释、配案例、出几道自测题、附上可核查的来源……"——这些要求其实是稳定的，每次变的只有概念名。

于是我把这套要求写成一份 SKILL.md 存进项目里，以后只需说"用 concept-learning 学 XXX"，AI 就会加载这份文档、按流程执行。

一句话总结：提示词是"一次性口头交代"，Skill 是"写进制度的流程"——它可以被版本管理、可以分享给团队、可以在一次次使用中迭代变好。它本质上是给 AI 的 SOP（标准作业程序）文档。

核心机制与组成

1. 文件形态：SKILL.md

---
name: concept-learning          # 技能名（供系统识别）
description: 概念学习资料生成器……  # 一句话说明"什么时候用我"（供触发匹配）
---
# 正文：适用场景 / 输入 / 步骤 / 输出 / 来源要求 / 自检要求

顶部 YAML 元数据中最关键的是 description：模型平时只能"看见"各技能的名字和描述，描述写得越准，触发就越准。

2. 加载机制：按需注入 + 渐进披露

  • 平时不占用上下文：技能列表只暴露 name + description 这点元信息；
  • 匹配时才加载：用户意图与某个 description 匹配，SKILL.md 正文才被读入当前上下文，成为行为指令；
  • 渐进披露：正文引用的脚本、参考资料等更深层内容，只在真正需要时才逐层加载——避免一次性塞满有限的上下文窗口。

3. 存放层级

层级位置适用
项目级仓库根目录 .workbuddy/skills/随仓库共享给团队，和项目一起版本管理（本作业采用）
用户级~/.workbuddy/skills/个人跨项目使用，不随某个仓库分发

4. 与相邻机制的关系

  • Tool（工具）给"能力"：让模型能调用 API、执行命令（新的"手脚"）；Skill 给"方法"：让它知道这类事该怎么做（"经验"）。
  • 微调改参数：Skill 不改模型权重，只在运行时往上下文注入指令——成本低、即时生效、删除即失效。

具体应用场景

场景：本作业本身（2026 年 9 月）。

仓库中的 .workbuddy/skills/concept-learning/SKILL.md 就是这个机制的实例。使用过程：

  1. 我在 WorkBuddy 中说："用 concept-learning 学习'Agent'这个概念"；
  2. WorkBuddy 匹配到该技能，把 SKILL.md 正文注入上下文；
  3. AI 严格按 Skill 定义的十步流程执行：定位概念 → 核实来源 → 写学习目标与核心问题 → 个人化解释 → 机制拆解 → 场景 → 辨析 → 自测 → 来源 → 自检；
  4. 产出 learning-materials/agent.html；随后学习"大模型的上下文"和"Skill"时，没有新增任何提示词，直接复用同一份 SKILL.md。

对比：如果没有 Skill，我学习第四个概念（比如 RAG）时，还得把整套要求重新口述一遍；现在只需要一句话。这就是"把任务知识沉淀成资产"。

概念辨析与使用边界

易混淆点辨析
Skill vs Tool/插件工具扩展模型的"能力"（能连什么 API、能执行什么命令）；Skill 沉淀"知识/流程"（知道事情该按什么步骤、什么标准做）。有工具没方法，模型用不好；有方法没工具，模型干不了。
Skill vs 提示词模板提示词模板是静态文本替换；Skill 有触发机制（description 匹配）、存放规范（目录 + 元数据）、可引用外部文件、可组合，且会被智能体平台统一管理和发现。
Skill vs 微调微调通过训练修改参数、成本高、更新慢；Skill 只注入上下文、零训练成本、改文件即更新。需要稳定的新"能力"用微调/工具，需要可演进的"做法"用 Skill。
Skill ≠ 万能Skill 不会赋予模型新能力（写一个"连数据库"的 Skill 并不能让它真的连上数据库——那需要工具）；Skill 写得臃肿反而挤占上下文。

好 Skill 的判断标准

  • description 精准：明确"什么时候用我、什么时候别用我"，触发才不会误判；
  • 流程可执行：步骤具体到模型能照做，而不是一堆形容词；
  • 输出结构明确：产出什么、存哪里、什么格式，写得清楚；
  • 带自检：有完成标准，模型能自己核对有没有达标。

课后自测（互动选择题）

点击选项作答：答对显示绿色、答错显示红色，并展开答案解析。全部作答后显示得分。

1. SKILL.md 顶部 YAML 元数据中的 description 字段，最主要的作用是？

✔ 正确答案：C。name 是技能的系统标识；description 说明"什么时候用我、什么时候别用我"。描述写得越精准，自动触发越准确、误触发越少——这也是官方 best practice 强调"先写好 description"的原因。

2. Skill 与 Tool 的本质区别是？

✔ 正确答案：B。"能力 vs 方法"。Skill 本质是一份带元数据的 Markdown 文档，通过注入上下文生效，不改变模型本身；Tool 则是模型可以调用的外部接口。

3. Skill 采用"渐进披露"（平时只暴露元数据，匹配后再加载正文）的主要原因是？

✔ 正确答案：C。这是一种上下文管理策略：技能可能有很多，若全部常驻会浪费 token 并稀释注意力。平时只占一行元数据，意图匹配时才注入正文——"最少且足够"原则的应用。

4. 项目级 Skill 与用户级 Skill 的适用对象分别是？

✔ 正确答案：B。区别在作用域：项目级服务于"这个仓库/这个团队"，随 Git 版本管理并共享给协作者；用户级服务于"这台机器上的我"，跨项目生效。本次作业的 concept-learning 就是项目级 Skill。
